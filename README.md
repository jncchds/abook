# ABook — Agentic AI Book Writing

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Docker Hub](https://img.shields.io/docker/v/jncchds/abook?label=Docker%20Hub)](https://hub.docker.com/r/jncchds/abook)
[![.NET](https://img.shields.io/badge/.NET-10-purple)](https://dotnet.microsoft.com/)

A self-hosted web application that uses AI agents to collaboratively write books. Seven specialized agents — Story Bible, Characters, Plot Threads, Chapter Outlines, Writer, Checker, and Editor — work together under your direction, streaming their progress in real time and pausing to ask clarifying questions when needed.

---

## Features

### Writing pipeline
- **Seven specialized agents** across two phases: a 4-phase Planner (Story Bible → Characters → Plot Threads → Chapter Outlines) and a per-chapter writing pipeline (Pre-write Check → Write → Check → Edit)
- **Checker → mechanical patch apply** — the Checker flags continuity, grammar, repetition, and style issues as structured JSON patches; the Editor applies them mechanically (no LLM call) using indexed text matching with whitespace normalization and position hints
- **Full synopsis spine** — every prior chapter's title and outline is injected into Writer and Editor messages so agents stay aware of the whole narrative and avoid recycling beats or re-introducing established characters
- **RAG context retrieval** — Writer runs 3 targeted queries (characters, locations, plot threads) and Editor runs 4 (same + repeated-phrase detection) against pgvector embeddings

### Planning & guidance
- **Guided planning Q&A** — before planning, the planner posts its clarifying questions to the book's **Clarifications** page and waits; answer each one there (or skip it), and submitting the last answer completes the round and planning carries on. Answers are kept as **clarifications** and added to the premise in every prompt, so nothing is lost if planning is interrupted, and the round isn't repeated once it's done. Edit, add, archive or restore them on the same page, or reopen the round to be asked again
- **Two ways to write a book** — **Interactive**: write it in a chat with the LLM, in any order, approving every change; **Autonomous**: the LLM plans the whole book and writes it on its own
- **Book chat (Interactive books)** — say what you want (a character, a plot thread, a chapter, a change); the LLM answers, flags **conflicts** with what the book already establishes, and proposes changes as cards with a diff — nothing changes until you **Apply** them, and every applied change can be **Undone**. No chapter count, no up-front outline: chapters are added at the end as you go, and each written chapter is summarized and checked, with the fixes proposed back in the chat. The premise and Story Bible are settled first and then **locked** while you write (only you can unlock them). Works on a phone; also available over MCP
- **Flexible workflow controls** — **Plan Book** and **Write Book** (both pick up where the book left off), **Illustrate Book**, per-section runs on the Chapters page (**▶ Write section** writes a section's unfinished chapters the way Write Book does, breaking it down first when the planner expects several chapters; **🔍 Check** checks each written chapter of it) and per-chapter runs on the chapter page (**✍️ Write / Rewrite**, **🖋 Edit prose**, **🔍 Check**); **Stop** cancels any running agent cleanly
- **Refresh-safe progress** — reloading the page (or losing the connection) mid-run keeps the current step, the latest progress message and everything streamed so far; new text continues where it left off
- **Interrupted runs keep their output** — if a Characters, Plot Threads, or Chapter Outlines run times out, drops, or is stopped part-way, everything that finished streaming is saved instead of discarded; run the phase again to pick up where it left off
- **Re-runs build on what exists** — regenerating a planning phase sends the current characters, plot threads, or outlines back to the model to refine and extend, rather than starting from a blank page; archived items stay out of it and are never overwritten

### Content management
- **Story Bible, Characters & Plot Threads** — generated by the Planner, fully editable, with per-item version history and snapshot restore
- **Inline editing** — edit book metadata, chapter titles/outlines, and add chapters manually without leaving the detail page
- **Sections and chapter order** — the plan is made of **sections**, each starting as one chapter. Insert anywhere (**＋ After** adds a section, **＋ Chapter here** adds a chapter to the same section, **＋ Insert at the start**), move chapters and sections up and down, and **✂ Split** a chapter that needs more room: divide its outline between it and a new chapter right after it in the same section, and both are written again (the old text stays in the version history). A section with several chapters keeps an overall plan of its own (**✎ Plan**), and the sidebar numbers its chapters "3.1", "3.2". **Plan Book** outlines sections (the target count is a number of sections) and notes which ones need more than one chapter; **⋔ Break down** has the planner divide an unwritten section into chapters, and Autonomous runs do it on their own before writing such a section. The Writer gets the section's overall plan and its other chapters, so each chapter tells its own share. Numbers follow the order, and plot threads' and characters' references (which count sections) move with them. Archived chapters and sections keep their place — **Show archived in place** shows them between their neighbours, and restoring puts them back there. Turn on **Show sections in the book** (Book Settings) to give each section a part heading ("I. Title") in the downloads and the reader
- **Version history** — chapters, characters, and plot threads all track history with preview and restore; soft-archive instead of delete. Every edit is kept as a version; a run of your own edits (web or Telegram) updates one version instead of piling up new ones, while any change by an agent or the book chat in between starts a new one
- **Archived means archived** — an archived chapter, character, or plot thread is kept purely so you can look at it or restore it. It is never sent to a model, never counted in planning or continuity checks, never included in an HTML/FB2/EPUB export or on the public reader page, and agents refuse to write to it
- **Book continuation** — create a sequel that copies all settings and inherits ancestor context; RAG and planning reference the full base-book chain
- **Rewind** — bring the whole book and its chat back to an earlier moment (before a chat message, after a chapter version, before or after a run). Every part gets the state it had then as a new version, so nothing in between is lost; later chat messages are hidden — see [Rewind](#rewind)

### Illustrations
- **AI illustrations with Z-Image or Unsloth Studio** — turn on **Illustrate this book** and the LLM plans illustrations for every finished chapter (what each image shows, where it goes, and its positive and negative prompts, chosen to suit the genre), plus the cover once the book is written. Review and edit the plan, then press **Illustrate book** to render everything in one image-model run — no LLM calls, so you can unload the LLM first (automatic for Ollama)
- **The same objects, clothes and places in every image** — the illustrator keeps a registry of recurring assets (props, outfits, places, creatures, vehicles) and repeats each one's description word for word whenever it appears; characters keep their usual outfit unless the story changes it. Review and edit the registry on the Illustrations page — an edit updates every prompt that shows the asset
- **One style for the whole book** — the illustrator writes an art direction once (style, a portrait composition shared by the whole cast, a book-wide negative prompt) from your visual style; it is added word for word to every image and can be edited on the Illustrations page
- **Consistent characters** — each character gets a visual description written from their profile and a reference portrait; every image showing them repeats that description, and scenes centred on them reuse the portrait's seed. Re-roll a portrait until the look is right, then re-render their scenes
- **Configurable** — image endpoint, steps, CFG, sizes and visual style live in the LLM configuration and presets, so applying a preset switches the text and image models together

### Exports & sharing
- **Multiple export formats** — HTML (6 colour themes, adjustable font size), EPUB, FB2, and a Metadata document (book info and stats, then the current Story Bible, clarifications, characters, plot threads and chapter plans, then the full timeline of planning, edits, agent messages and LLM calls). Rendered illustrations and the cover are embedded in all of them, compressed to JPEG to keep the download small
- **Public Library** — browse and read published books without logging in (when public mode is enabled); each chapter has its own URL for bookmarking and sharing
- **Telegram bot** — connect a book to a Telegram chat, group topic or channel: a pinned status card with Start / Continue / Stop, the planner's questions (reply to answer), a file after each chapter edit, the finished book, illustrations, live drafts while a chapter is written, and the book chat of Interactive books. Whoever can post in the chat gets the access you choose — see [Telegram Bot](#telegram-bot)

### Infrastructure
- **Pluggable LLM backend** — Ollama (default, local), OpenAI (or any OpenAI-compatible API), or Google AI Studio; settings kept as presets (your default is copied into each new book) and per book
- **Real-time streaming** — watch chapters being written token by token via SignalR; planning phases stream with live progressive JSON previews. Only book content streams — a reasoning model's thinking is saved to the chat as one "💭 Thinking" message when each step finishes (even when it fails), and the live view reconnects by itself after a network drop. Live updates are numbered, so after a drop the page gets exactly the updates it missed replayed; a heartbeat every 15 seconds notices a connection that died silently and reconnects it
- **Fail-safe runs** — a stalled LLM connection times out instead of hanging the book; double-clicking a start button can't launch two runs; runs interrupted by a server restart are closed out with a note telling you how to pick up (**Plan Book** / **Write Book**, or `/plan` / `/continue` in Telegram)
- **Health endpoint** — `GET /health` reports whether the database is reachable (for Docker/uptime checks)
- **Token usage statistics** — per-agent prompt and completion token counts, persisted to the database and displayed in a collapsible panel. Calls that error, time out, or are cancelled are recorded too, with a Status column and the failure reason shown next to their partial counts
- **MCP server** — built-in Model Context Protocol server at `/mcp`; connect Claude Desktop, VS Code Copilot, or any MCP client using a per-user API token
- **Multi-user** — JWT sign-in (short-lived access token, httpOnly refresh cookie) with an admin role for user management
- **Ollama model management** — browse installed models, pull new ones with live progress
- **Global concurrency limit** — cap simultaneous agent runs across all books/users with `AgentSettings__MaxConcurrentRuns`
- **PWA support** — installable, works offline for cached content

## Architecture

```
[React SPA — served as static files from ASP.NET wwwroot]
        ↕ REST API + SignalR
[ASP.NET Core 10 API]
        ↕ Direct provider SDKs      ↕ EF Core 10 + Npgsql
[LLM (Ollama / OpenAI / Google)]   [PostgreSQL 16 (pgvector in-DB)]
```

React is built at image-build time and served from `wwwroot/` — there is no separate frontend container at runtime.

## Quick Start

### Prerequisites

- [Docker](https://docs.docker.com/get-docker/) + [Docker Compose](https://docs.docker.com/compose/)
- [Ollama](https://ollama.com/) running on the host machine (or any OpenAI-compatible API)

### Run with Docker Compose

```bash
docker-compose up -d

# App is available at
open http://localhost:5000
```

On first launch the app shows a **Create Admin Account** setup screen — the first account registered automatically becomes admin. After signing in, go to **Settings** to configure your LLM provider and pull an Ollama model.

### Run from Docker Hub

```bash
docker run -d \
  -p 5000:8080 \
  -e ConnectionStrings__DefaultConnection="Host=<postgres-host>;Port=5432;Database=abook;Username=abook;Password=abook" \
  --add-host host.docker.internal:host-gateway \
  jncchds/abook:latest
```

> PostgreSQL with the pgvector extension must be reachable. The compose file below starts it automatically.

### Sign-in

> ⚠️ **Since v0.3.0 ABook uses JWT sign-in instead of cookie sessions.** Everyone has to sign in once after updating; books, presets and MCP API tokens are not affected.

The browser gets a short-lived access token (kept in memory, never in storage) and a refresh token in an httpOnly cookie that is only sent to `/api/auth`, rotated on every use and revocable (sign-out, password change). A browser stays signed in for `Jwt__RefreshTokenDays` after its last visit.

Tokens are signed with `Jwt__SigningKey`. **You don't have to set it** — if it is missing, ABook generates a random key on first start and keeps it in its database, so sessions survive restarts and updates. It does log a ⚠️ warning at every startup and shows admins a banner, because anyone with a copy of the database could then forge sign-ins. To move the key into your configuration:

```bash
docker compose exec abook-api dotnet ABook.Api.dll secrets show
```

Copy the printed `Jwt__SigningKey=…` line into the `environment:` section of `abook-api`, then `docker compose up -d` (any other random 32+ character value works just as well). Changing the key never signs anyone out: it only invalidates access tokens, and browsers fetch a new one with their refresh cookie.

### LLM Providers

LLM settings are kept as **presets** (the 🔑 Presets page) and per book (each book's **Settings** page):

| Provider | Notes |
|---|---|
| **Ollama** | Default. Runs locally; `host.docker.internal` resolves to the host from inside Docker. |
| **OpenAI** | Provide an API key and model name (e.g. `gpt-4o`). Leave endpoint blank for the real OpenAI API; set a custom endpoint for any OpenAI-compatible API (Groq, Together, LM Studio at `http://host.docker.internal:1234/v1`, etc.). |
| **Google AI Studio** | Native Gemini connector. Requires an API key from [aistudio.google.com](https://aistudio.google.com/apikey). Suggested models: `gemini-2.0-flash`, `gemini-2.5-pro`. Embedding model: `text-embedding-004`. |
| **OpenAI Compatible** | For LM Studio, OpenRouter, vLLM and similar. Reads the stream directly, so non-standard fields such as `reasoning_content` are captured; `reasoning_effort` is never sent. API key optional. |

How the settings are resolved:

- **Every book has its own LLM settings.** When you create a book it gets a copy of your **default preset** (a sequel copies its base book instead). Later changes to the preset — or picking another default — never affect existing books; change those on the book's Settings page (where **Apply Preset** copies a preset in).
- **Your default preset** is chosen under **Settings → Default LLM Preset** or with **Make default** on the Presets page. New users get a private "Default" preset built from the `LlmDefaults__*` environment variables, if those are set.
- **Shared presets** are available to every user (including as their default) but only admins can create, edit or delete them. Admins share a preset with the **Shared with everyone** toggle; sharing cannot be undone. Anyone who can use a shared preset can see its API keys once it is copied into their books.
- There is no global or per-user fallback configuration any more (removed in v0.3.0).

Local models often ignore the JSON schema the planning agents send — returning a chapter number as `1.0` or `"3"`, or a text field as a list. The parsers coerce those instead of failing, drop only the entries they genuinely cannot read, and post a `⚠️` note in the book's chat naming each dropped entry and the JSON behind it. If a planning phase does fail outright, the error in the chat quotes what the model actually returned.

### Image Generation (Illustrations)

Illustrations are rendered by one of two image providers, chosen under **🎨 Image Generation** in a book's LLM settings or in a preset; use **Test connection** after setting the URL.

- **Z-Image** — a self-hosted [Z-Image Turbo](https://huggingface.co/Tongyi-MAI/Z-Image-Turbo) server: the FastAPI server in the adate project's `compose/zimage` folder (`POST /generate`, `GET /images/{id}`, `GET /health`).
- **Unsloth Studio** — the image models of an [Unsloth Studio](https://unsloth.ai/docs/new/studio) server. Enter the Studio address (with or without `/v1`) and an API key from Studio's **Settings → API**. Studio keeps only one model on the GPU, so if it also serves your text model (as an **OpenAI Compatible** provider at `http://<host>:<port>/v1`), set **Image model** too — e.g. `unsloth/Z-Image-Turbo-GGUF:z-image-turbo-Q8_0.gguf` (a Hub repo id, optionally `:` plus a checkpoint file). ABook then loads it before rendering whenever no image model is loaded, and Studio unloads the text model to make room. Leave it blank to use whatever is loaded on Studio's Images page.

| Setting | Default | Notes |
|---|---|---|
| Endpoint | — | Blank disables rendering (illustrations can still be planned) |
| Image API key | — | Unsloth Studio only |
| Image model | — | Unsloth Studio only — loaded when Studio has no image model loaded |
| Visual style | — | Written into every prompt by the LLM; blank lets it choose one for the genre |
| Steps / CFG | 8 / 1.0 (Unsloth Studio: 9 / 0) | Z-Image Turbo values; blank on Unsloth Studio lets Studio choose, so set both for other Studio models (e.g. FLUX). Negative prompts only take effect with CFG above 1.0 |
| Portrait / landscape size | 768×1152 / 1152×768 | Square images use the portrait area |
| Timeout | 300000 ms | Per image |
| Unload the LLM before rendering | off | Ollama only (`keep_alive: 0`); Unsloth Studio swaps models by itself |

Workflow: enable **Illustrate this book** in the book settings → write the book → open **🎨 Illustrations**, review or edit the plan → **Render portraits** and re-roll any you don't like → **Illustrate book**.

### Rewind

**⏪ Rewind** (book sidebar) brings the whole book back to how it was at a moment you pick from a list: before one of your book-chat messages, after a reply, after a chapter version, or before/after an agent run.

- **Preview first** — every section, chapter, the Story Bible, characters, plot threads, clarifications, book fields (title, premise, planning progress) and book-chat suggestion that would change, and how many chat messages get hidden. Nothing happens until you confirm.
- **A new state, not a deletion** — each part gets the state it had then *as a new version* (a chapter gets a new version, the Story Bible a new snapshot, characters and threads a new version). Everything in between stays in each part's history, where you can still open or restore it. Parts created since are archived; parts deleted since come back.
- **The chat** — messages after the moment are collapsed ("⏪ rewound") and never sent to the LLM again; the chat's rolling memory goes back to what it was then. Suggestions applied since are open again. There is no fast-forward.
- Settings (prompts, LLM, mode, language, art direction) and illustrations are not rewound. A rewind is refused while an agent runs.
- It works from a change log that records every change to the book's content. The log starts when you first run v0.5.0, so a book can be rewound to any moment from then on.

Also over MCP (`list_rewind_points`, `preview_rewind`, `rewind_book`) and in Telegram (`/rewind`).

### Telegram Bot

One bot per ABook server lets people follow and steer a book from Telegram.

**Setup**
1. Create a bot with [@BotFather](https://t.me/BotFather) and set `TELEGRAM_BOT_TOKEN`.
2. In BotFather, turn **privacy mode off** (Group Privacy → Disable) so the bot sees every message in its groups. Leave **topic mode in private chats** off: the bot doesn't use topics there (with it on, Telegram starts a new topic for every message you send outside one). A private chat follows one book; follow more books in groups or their topics.
3. If the server is reachable over HTTPS, set `ABOOK_HOSTNAME` (Telegram then posts updates to `https://{ABOOK_HOSTNAME}/api/telegram/webhook` — ports 443, 80, 88 or 8443). Without it the bot polls Telegram, which works behind NAT too.

**Connecting a book** — Book Settings → **Telegram** → choose the access → **Connect a chat**. Use the one-time code (valid 15 minutes) with one of: *Open a private chat with the bot*, *Add the bot to a group*, or send `/bind CODE` in a forum topic or post it in a channel where the bot is an admin. **Everyone who can post in that chat or topic gets the access you chose** — nobody signs in on the Telegram side:

| Access | Can |
|---|---|
| Read | See the status card, notices and files |
| Participate *(default)* | …and answer the planner's questions, `/export`, `/note`, write in the book chat (Interactive books) and apply / reject / undo what it suggests |
| Control | …and start, continue, plan and stop runs, `/rewind`, `/unbind`. Runs use the book's LLM settings, so everyone there spends its tokens; in groups you can limit starting and stopping to the chat's admins (rewind and disconnect are always admins-only in groups) |

**In the chat**
- A pinned **status card** shows what the agents are doing, the chapters done and the tokens of the current run, with **Stop / Start / Continue**, **Plan only** (before the book is planned: plan it and stop for review), **Refresh** and **Export** buttons for the chat's access.
- The planner's questions are asked one at a time: **reply to the question message** to answer it, or press **Skip**. Other messages never count as answers.
- **A file after each chapter edit** (EPUB, FB2 or HTML — set per chat), sent as a reply to the chapter's previous version; the planning document when planning completes; the whole book when the last chapter is done; rendered illustrations as photos.
- In a private chat the chapter being written shows as a **live draft** (with a stop button for Control).
- **Interactive books**: write in the chat to talk to the book chat. Its suggested changes come with buttons: ✅ / ✖️ per suggestion, **tick boxes** (☐/☑) to pick several and **Apply ticked** / **Reject ticked** them together, **Apply all** / **Reject all**, one button per alternative (option A/B), and ↩️ Undo. Or reply to the suggestions with their numbers — `1 3`, `apply 1, 3`, `reject 2`.
- **Rewind**: reply `/rewind` to any message of the thread to rewind the book to when it was posted (to just before it, for your own book-chat message), or send `/rewind` alone to pick a recent moment from buttons. The bot shows the preview with **⏪ Rewind** / **Cancel** (valid 10 minutes); after the rewind every connected thread gets a divider message, rewound chat replies are crossed out, and changed chapters arrive as new file versions. Control only — and in groups only the chat's admins.
- `/book` — the book's card (see below), for the book's owner and for everyone with Participate access in that chat. Participate can view everything, edit the Story Bible, characters, plot threads and chapter outlines, answer clarifications and download; the book's settings, archiving, restoring versions and writing/checking chapters need Control. Only the person who opened a card can use it.
- Commands: `/status`, `/run`, `/continue`, `/plan`, `/stop`, `/export [epub|fb2|html|metadata]`, `/note text`, `/questions`, `/rewind`, `/book`, `/unbind`, `/help`.

**Your account and your books** — link your Telegram account in **Settings → Telegram** (a one-time link). Then, in the private chat with the bot:
- `/newbook` — a wizard card: reply to it with the title and premise, pick genre, language, mode and chapter count, **✅ Create**. It uses your default LLM preset, and the card turns into the new book's card.
- `/books` — your books; tap one to see and edit it in the same card. Opening a book doesn't follow it anywhere.
- The **book card**: its settings and LLM preset, the Story Bible, characters, plot threads, **sections** (edit a section's plan, add a chapter to it, move it, ⋔ break it down into chapters, **✍️ Write section** / **🔍 Check section** in Autonomous books, archive it), chapters (with ⬆️/⬇️ to move them) and clarifications, **🔒 Lock bible & start writing** for Interactive books, and **⬇️ EPUB / FB2 / HTML / 🗂 Metadata** downloads. Cards are single messages edited in place: tap ✏️ on a field, **reply to the card** with the new text, then **💾 Save**. Add, archive and bring back characters, threads and chapters, see **🕘 Versions** and restore one, read a chapter as a file, write or check a chapter. Chapter text isn't edited in Telegram.
- **Following a book** is explicit: the card's **🔗 Chats** lists the chats that follow the book (each with *disconnect*) and makes a one-time code for the access you pick (Read / Participate / Control) — the same code as Book Settings → Telegram, with a link for this private chat, a link to add the bot to a group, and `/bind CODE` for a topic or channel.
- `/unlink`, `/account`.

As the owner you also have full rights in every chat connected to your books. Each suggestion of the book chat has a **details** link that shows exactly what it changes. The bot uses Telegram's rich messages (headings, tables, collapsible sections, links inside the text); on a Bot API server without them it falls back to plain messages with buttons.

Answers, notes and chat messages from Telegram are marked with who sent them (✈️ Telegram · @name · chat) in ABook. Disconnect a chat from Book Settings, with `/unbind`, or by removing the bot; deleting the book disconnects its chats.

## Agent Workflow

```
Autonomous books (Interactive books are written in the book chat — see below):

User creates book (title, premise, genre, target chapters)
         │
         ├─ optional: choose a base book (settings + context copied)
         │
         ▼
  ┌──────────────────────────────────────────────────────┐
  │  Planner — 4-phase pipeline                          │
  │   Phase 1: Story Bible (world-building, tone, rules) │
  │   Phase 2: Character Cards (roles, arcs, goals)      │
  │   Phase 3: Plot Threads (subplots, themes, arcs)     │
  │   Phase 4: Chapter Outlines (title + synopsis each)  │
  │                                                      │
  │   Asks clarifying questions up front                 │
  └──────────────────────────────────────────────────────┘
         │
         │  ← "Plan Book" stops here so you can review
         │    and edit outlines before clicking "Write Book"
         ▼
  For each chapter:
  [Checker]  ── pre-write: checks outline for contradictions
         │
         ▼
  [Writer]  ── writes full chapter prose
         │
         ▼
  [Checker]  ── continuity + style review → structured JSON patches
         │
         ▼
  [Editor]  ── applies patches mechanically (skipped if no issues)
         │
         ▼
  [Editor]  ── creative rewrite — only when the Checker asked for one
         ▼
      Done ✓
```

Agents stream tokens via SignalR as they write.

**Workflow controls:**

| Button | Behaviour |
|---|---|
| **Plan Book** | Runs only the incomplete planning phases and stops so you can review outlines |
| **Write Book** | Full pipeline (idempotent — skips completed phases and Done chapters, so it also resumes an interrupted run) |
| **Illustrate Book** | Renders the planned illustrations (shown when illustrations are enabled) |
| **▶ Write section** / **▶ Write** (Chapters page) | One section as Write Book writes it: broken down first when the planner expects several chapters, then pre-check → write → check → fixes for each chapter not Done (a one-chapter section shows it on the chapter as **▶ Write**) |
| **🔍 Check** (Chapters page) | Checks each written chapter of the section, one at a time; findings arrive in Agent Messages |
| **✍️ Write / Rewrite**, **🖋 Edit prose**, **🔍 Check** (chapter page) | One agent on one chapter: the Writer from the outline, the Editor on the prose, or a continuity check of that chapter |
| **Stop** | Cancels any running agent cleanly |

Interactive books have none of these: their chapters are written, edited and checked from the book chat.

### Interactive books — the book chat

Choose **Interactive** when you create a book (Autonomous is the default; the mode can be changed in Book Settings). The book opens on **Book Chat**, which waits for you: check the premise and the LLM preset first, then press **Start the book chat**.

1. **Foundation.** The LLM reads your premise, proposes a Story Bible and asks what it needs to know. Discuss it, add characters and plot threads, and apply the changes you like. When the world feels settled, press **Lock bible & start writing** (writing the first chapter locks it too).
2. **Writing.** Ask for whatever comes next, in any order — "introduce Tobin, Mara's old partner", "add a chapter where…, and write it", "make chapter 3 darker". New chapters go at the end unless you ask otherwise — a chapter not written yet can be inserted earlier, moved or removed ("add a chapter between 3 and 4 where…"); written chapters stay where they are. There is no chapter count to reach and no outline to plan up front.
3. **Every change is a proposal.** Each reply shows its changes as cards — **Show changes** for a diff, **Apply**, **Reject**, **Apply all**, or tick the cards you want and **Apply selected**; applied changes have **Undo**. Several passage fixes of one chapter applied together become a single edit (one chapter version), undone as one. Applying several chapter writes (or revisions) at once runs them **one chapter at a time**: the first is written and checked, the others wait as **Queued** until you have applied or rejected that chapter's follow-up suggestions, so each chapter builds on the reviewed one before it. **Start now** skips the wait; **Cancel** drops a queued one. Every set of suggestions has an **Anything else?** box: write what else to change (or leave it empty) and **Revise suggestions** — the co-author gets the suggestions with your note and answers with a complete corrected list that replaces them. In Telegram, reply to the suggestions with your note. When a request contradicts the book (the Story Bible, a character, something a written chapter established), the reply lists the **conflicts** and offers alternatives: adapt the request (option A) or change the book to fit it (option B).
4. **Next steps come as cards.** Once you apply a chapter's outline, a **Write Chapter N** card appears right away — no need to ask for it (for a chapter that is already written, a card to revise it to the new outline).
5. **After a chapter is written** it is summarized (the summary is what later prompts use as "the story so far") and checked; the fixes the checker suggests, the new characters the chapter introduced and plot threads it moved on are proposed in the chat for you to apply.
6. **Run a step again on request.** Ask "check the outline of chapter 5", "re-check chapter 3" or "summarize chapter 2 again" and the reply offers a card for it — **Outline check**, **Continuity check** or **Summary** — with **▶ Run**. It changes nothing by itself: what it finds comes back as new proposals (a corrected outline; patches or a revision; new characters and plot-thread changes). A finished step can be run again with **↻ Run again**.

While writing, the premise and Story Bible are **locked**: the chat cannot change them and the Story Bible page is read-only. You can unlock them in **Book Settings** if you really need to — the LLM never does.

Each request sends the LLM a compact digest of the book plus only the last few messages (older ones are kept as a short running summary), so long chats stay fast and cheap. The page works on a phone. Over MCP: `send_book_chat_message`, `get_book_chat`, `revise_book_chat_suggestions`, `retry_book_chat_message`, `apply_book_chat_proposals`, `reject_book_chat_proposals`, `undo_book_chat_proposal`, `start_book_chat`, `lock_story_bible`. In Telegram, the book card has **🔒 Lock bible & start writing**.

**Letting the chat read parts of the book.** That digest holds only summaries of written chapters and one line per character, so a request like "in chapter 3, change what Mara says at the gate" makes the LLM work from memory. Turn on **Let the book chat read parts of the book** in Book Settings — or just ask the chat to turn it on and apply its **Setting** card — and the LLM may first ask for the parts it needs in full (chapter text, chapter plans, character cards, plot threads; up to 6 per reply). The chat shows "📖 Reading Chapter 3, Mara before replying…", the app sends those parts back, and the answer to that is the reply. It costs a second LLM call only when the LLM asks for something. Off by default; also `chatPartRequestsEnabled` in MCP `update_book`.

Chapter edits you make by hand are re-embedded in the background, so retrieval for later chapters sees your text rather than the version the agent wrote.

For books created from a base book, chapter-level RAG retrieval includes embeddings from all ancestor books in the continuation chain.

## Development

### Prerequisites

- [.NET 10 SDK](https://dotnet.microsoft.com/download)
- [Node.js 20+](https://nodejs.org/)
- Docker (for PostgreSQL with pgvector)

### Local Setup

```bash
# Start PostgreSQL
docker-compose up postgres -d

# Start the UI dev server (proxies API calls to localhost:5000)
cd src/abook-ui
npm install
npm run dev

# Start the API (second terminal)
cd src/ABook.Api
dotnet run --urls http://localhost:5000
```

The React dev server runs at `http://localhost:5173` and proxies `/api` and `/hubs` to the ASP.NET server.

### Database Migrations

```bash
dotnet ef migrations add <MigrationName> --project src/ABook.Infrastructure --startup-project src/ABook.Api
dotnet ef database update --project src/ABook.Infrastructure --startup-project src/ABook.Api
```

Always use the `dotnet ef` CLI — never create migration files by hand.

### Build Docker Image

```bash
docker build -t abook .
```

The multi-stage Dockerfile builds the React app (Node 20), compiles the .NET API (.NET 10 SDK), and produces a minimal runtime image (ASP.NET 10).

### LLM Debug Logging

Set `LLM_DEBUG_LOGGING=true` to print the full chat history and LLM responses to the application log at `Information` level.
