# Plan: Agentic Book-Writing ASP.NET Core App

## TL;DR

Build a Docker-packaged ASP.NET Core 10 web app with a React (TypeScript/Vite) UI **served as static files from wwwroot** (NOT a separate Docker service) that uses Semantic Kernel to orchestrate four AI agents (Planner, Writer, Editor, Continuity Checker) for collaborative book writing. Agents stream progress via SignalR and can pause to ask the user plot-clarifying questions. PostgreSQL stores relational data; **pgvector** (PostgreSQL extension) stores chapter embeddings for RAG-based context retrieval. LLM provider is pluggable (Ollama by default, swappable to OpenAI/Azure via configuration). Multi-user with JWT authentication (short-lived access token + rotating refresh cookie).

---

## Architecture Overview

```
[React SPA (static files in ASP.NET wwwroot — single container)] 
    ↕ REST API + SignalR
[ASP.NET Core 10 API]
    ↕ Semantic Kernel (pluggable LLM connector)
    ↕ EF Core + pgvector
[PostgreSQL (Docker, pgvector/pgvector:pg16)]    [Ollama (host machine)]
```

Docker Compose runs: **ASP.NET app (with React static files baked in) + PostgreSQL**. Ollama is external on the host. React is NOT a separate service — it's built in a Dockerfile stage and copied into `wwwroot/`.

## Data Model

- **Book**: Id, Title, Premise, Genre, TargetChapterCount, Status (Draft/InProgress/Complete), Language, StoryBibleSystemPrompt, CharactersSystemPrompt, PlotThreadsSystemPrompt, ChapterOutlinesSystemPrompt, WriterSystemPrompt, EditorSystemPrompt, ContinuityCheckerSystemPrompt, **IllustratorSystemPrompt**, **HumanAssisted** (bool, default false), **IllustrationsEnabled** (bool, default false), **IllustrationStyle / IllustrationPortraitFraming / IllustrationNegativePrompt** (the book's art direction) + **IllustrationStyleSource** (the configured visual style it was written from), **BaseBookId** (nullable self-FK → Book), **SettingsCopiedAt** (nullable UTC timestamp), UserId (FK → AppUser), CreatedAt, UpdatedAt
- **Chapter**: Id, BookId, Number, Title, Outline, Content (markdown), Status (Outlined/Writing/Review/Editing/Done), CreatedAt, UpdatedAt
- **AgentMessage**: Id, BookId, ChapterId (nullable), AgentRole, MessageType (Content/Question/Answer/SystemNote/Feedback), Content, IsResolved, **IsOptional** (bool, default false), **QuestionMessageId** (nullable, no FK — on Answer messages saved since v0.3.0: the Question it answers, set by `ResumeWithAnswerAsync`), CreatedAt
- **LlmConfiguration**: Id, **BookId (required, unique, FK → Book, cascade)**, Provider (Ollama/OpenAI/GoogleAIStudio), ModelName, Endpoint, ApiKey (nullable), EmbeddingModelName (nullable), Temperature, TimeoutMs, ReasoningEffort, MaxTokens
  - **Book-only — no fallback** (since v0.3.0). Each book owns one configuration, copied from the owner's default preset when the book is created (`BookRepository.AddAsync`) or from the base book for a sequel. A book is never tied to a preset afterwards. `GetLlmConfigAsync(bookId)` returns only that row; agents throw `LlmConfiguration.MissingMessage` when it is missing. There is no user-level or global configuration any more.
  - Full copies go through `LlmSettingsCopy.CopyFrom` (preset → config, config → config, preset → preset).
  - **Image-generation fields** (`IEditableImageGenSettings`, shared with LlmPreset): ImageProvider (`ZImage` | `UnslothStudio`), ImageEndpoint (null = image generation off), ImageApiKey (bearer token, plaintext like ApiKey), ImageModel (Unsloth Studio: model loaded when none is), ImageSteps, ImageCfg, ImagePortraitWidth/Height, ImageLandscapeWidth/Height, ImageTimeoutMs, ImageVisualStyle, **ImagesPerChapter** (base number of illustrations the planner aims for per chapter; it may go over), UnloadLlmBeforeRender. Null numbers fall back to `ImageGenDefaults` (Z-Image Turbo: 8 steps, cfg 1.0, 768×1152 / 1152×768, 2 images per chapter). Copied with `CopyImageSettingsFrom` everywhere a config or preset is copied.
- **LlmPreset**: Id, UserId (nullable, FK → AppUser, **cascade** — a user's private presets are deleted with them and never turn shared), Name, Provider, ModelName, Endpoint, ApiKey (nullable), EmbeddingModelName (nullable), the image-generation fields above, CreatedAt, UpdatedAt
  - Visible to: own presets (UserId = currentUser) + **shared** presets (UserId = null)
  - Shared presets: usable by everyone (including as a default), created/edited/deleted only by admins (`PresetRequest.Shared`). Sharing is one-way: an admin may share their own preset, but a shared preset is never made private again because other users may have it as their default.
  - Managed via `GET/POST /api/presets`, `PUT/DELETE /api/presets/{id}`, `GET /api/presets/default`, `PUT /api/presets/{id}/default`
- **AppUser.DefaultPresetId** (nullable FK → LlmPreset, set null on delete): the preset copied into each new book. `IBookRepository.GetDefaultPresetAsync(userId)` returns it only while it is still the user's own or shared. A new user gets a private "Default" preset built from the `LlmDefaults` section (`UserProvisioningService`, used by register and admin user creation) when it names a provider; otherwise they start without one and must pick or create a preset.
- **LLM Presets page**: `Presets.tsx` at `/presets` route. Lists own + shared presets with "★ default" / "shared" badges and a "Make default" button; Edit/Delete only on presets the user may change (own, or shared for admins). Admins get a "Shared with everyone" toggle.
- **Settings page**: the "Default LLM Preset" section is a dropdown of visible presets (`PUT /api/presets/{id}/default`). The Ollama pull section shows when the default preset uses Ollama. There is no LLM form on the Settings page any more — book settings live on each book's Settings page, which still has "Apply Preset" (pre-fills the form) and "Save as Preset…".
- **Two settings pages**: `GlobalSettings.tsx` at `/settings` (MCP Access + LLM config global scope + Ollama pull); `BookSettings.tsx` at `/books/:bookId/settings` (LLM config book-scoped + language + agent system prompt overrides). Old unified `Settings.tsx` deleted.
- **CharacterCard** (illustration fields): **VisualPrompt** (canonical appearance wording, LLM-written, editable), **VisualPromptSourceHash** (hash of Name + PhysicalDescription it was written from), **ImageSeed** (long?, shared by the portrait and the character's scenes)
- **Illustration**: Id, BookId, ChapterId (null for Cover/Portrait), Kind (Scene/Cover/Portrait), CharacterCardId (Portrait), ParagraphNumber (1-based hint) + AnchorText (short quote), Caption, Prompt, NegativePrompt, Orientation (Portrait/Landscape/Square), FocusCharacterId, CharacterNamesJson, Seed (re-roll override), Status (Planned/Rendered/Failed), Error, ImageId, SortOrder
- **VisualAsset**: Id, BookId, Name (unique per book), Kind (Object/Outfit/Location/Creature/Vehicle/Other), Description (canonical English wording repeated word for word in every prompt that shows it), CharacterCardId (set for a character's usual outfit; SetNull on delete, re-linked by name `"{Name} — usual outfit"`), FirstChapterNumber
- **BookImage**: Id, BookId, Data (bytea), ContentType, Width, Height, Seed — kept apart from Illustration so listings never load bytes; a re-render stores a new row and deletes the old one, so image ids are immutable (served with `Cache-Control: immutable`)
- **AppUser**: Id, Username, **DisplayName (nullable)**, PasswordHash, IsAdmin, **ApiToken (nullable GUID string)**, CreatedAt

### Vector Store (PostgreSQL + pgvector)
- **ChapterEmbedding** — `ChapterEmbeddings` table in PostgreSQL, stores chunked chapter text with embeddings
  - Each chapter is split into ~500-token overlapping chunks
  - Metadata: BookId, ChapterId, ChapterNumber, ChunkIndex
  - Used by agents for RAG: query relevant passages across all chapters without exceeding context window
  - Embedding model: configurable (default: Ollama embedding model or OpenAI `text-embedding-3-small`)
  - `vector` column type (dimension-free, supports any embedding model)
  - Unique index on `(BookId, ChapterId, ChunkIndex)` + index on `BookId`

## Agent Roles & Workflow

### Planner Agent
- Input: Book premise + user guidance
- Output: Chapter outlines (title + synopsis per chapter)
- Can ask: "Should the story have a subplot about X?" etc.

### Writer Agent
- Input: Chapter outline + previous chapters' summaries (for context)
- Output: Full chapter content in markdown

### Editor Agent
- Input: Written chapter
- Output: Edited chapter + list of suggested changes

### Continuity Checker Agent
- Input: All chapters written so far
- Output: List of inconsistencies + suggested fixes

### Human-in-the-Loop Flow
1. Agent encounters ambiguity → calls `AskUserAndWaitAsync` in `AgentBase`
2. Persists `AgentMessage` (type=Question) + notifies UI via SignalR
3. Registers a `TaskCompletionSource<string>` in `AgentRunStateService.SetPending`
4. Sets run state to `WaitingForInput`; `await tcs.Task` blocks the agent coroutine
5. SignalR pushes `AgentQuestion` event to React UI; answer form appears in chat panel
6. User types answer → `POST /api/books/{id}/messages/answer` → `AgentOrchestrator.ResumeWithAnswerAsync`
7. `TryResolvePending` calls `tcs.SetResult(answer)` → agent resumes with answer injected into context
8. Cancellation (Stop button) calls `CancelRun` which cancels the CTS and calls `tcs.TrySetCanceled()`

### Phase 1: Project Scaffolding & Infrastructure
1. Create solution structure:
   - `ABook.slnx` (VS Solution XML format, requires .NET 9+ SDK)
   - `src/ABook.Api/` — ASP.NET Core Web API project (.NET 10)
   - `src/ABook.Core/` — Class library (domain models, interfaces)
   - `src/ABook.Infrastructure/` — Class library (EF Core, LLM connectors)
   - `src/ABook.Agents/` — Class library (Semantic Kernel agent definitions)
   - `src/abook-ui/` — React + TypeScript + Vite app
2. Set up Docker infrastructure:
   - `Dockerfile` (multi-stage: build .NET + build React → final runtime image with static files in wwwroot)
   - `docker-compose.yml` (app + PostgreSQL with pgvector, with `extra_hosts` for host Ollama access)
   - `.dockerignore`
3. Configure PostgreSQL with EF Core (Npgsql):
   - `AppDbContext` with entities from data model
   - Initial migration
   - Connection string from environment variables / `appsettings.json`
4. Configure pgvector:
   - `IVectorStoreService` interface in `ABook.Core`
   - `PgvectorVectorStoreService` in `ABook.Infrastructure.VectorStore` using `Pgvector.EntityFrameworkCore`
   - `ChapterEmbedding` EF Core entity in `ABook.Infrastructure.VectorStore`
   - EF migration `AddChapterEmbeddings` creates `CREATE EXTENSION IF NOT EXISTS vector` + `ChapterEmbeddings` table

### Phase 2: Backend Core (API + SignalR) — *depends on Phase 1*
5. Define domain models in `ABook.Core`:
   - `Book`, `Chapter`, `AgentMessage`, `LlmConfiguration` entities
   - `BookStatus`, `ChapterStatus`, `AgentRole`, `MessageType` enums
   - `IBookRepository`, `IAgentOrchestrator`, `ILlmProviderFactory`, `IVectorStoreService` interfaces
6. Implement EF Core repositories in `ABook.Infrastructure`
7. Build REST API controllers in `ABook.Api`:
   - `BooksController` — CRUD for books
   - `ChaptersController` — CRUD for chapters within a book
   - `MessagesController` — post answers, get conversation history
   - `ConfigurationController` — manage LLM provider settings
   - `AgentController` — start/stop agent runs; returns 202 immediately (fire-and-forget)
   - `AuthController` — login, register, logout, current user (`/api/auth/me`)
   - `UsersController` — admin-only user CRUD (create, change password, toggle role)
   - `ModelsController` — `GET /api/models` (proxy to Ollama `/api/tags` + OpenAI/Google model lists), `POST /api/ollama/pull` (SSE stream). Replaced the old separate `OllamaController`.
8. Set up SignalR hub (`BookHub`):
   - Methods: `JoinBook(bookId)`, `LeaveBook(bookId)`
   - Events: `AgentStreaming(bookId, chapterId, token)`, `AgentQuestion(bookId, message)`, `AgentStatusChanged(bookId, agentRole, status)`, `ChapterUpdated(bookId, chapterId)`

### Phase 3: Agent Engine (Semantic Kernel) — *depends on Phase 2*
9. Configure Semantic Kernel with pluggable LLM connector:
   - `ILlmProviderFactory` that creates SK `IChatCompletionService` based on `LlmConfiguration`
   - Support Ollama via `OllamaApiClient` / OpenAI-compatible endpoint
   - Support OpenAI, Azure OpenAI, Google AI Studio connectors behind same interface
10. Implement vector store integration for RAG:
    - On chapter save/update → chunk text → generate embeddings → upsert to `ChapterEmbeddings` table via pgvector
    - `RetrieveContext(bookId, query, topK)` method for agents to pull relevant passages
    - Agents use retrieved context instead of full chapter text to stay within context window
11. Implement agent orchestrator (`AgentOrchestrator`):
    - Manages agent run lifecycle (start, pause, resume, complete)
    - Fire-and-forget execution via `RunInBackground` helper using `IServiceScopeFactory`
    - `AgentRunStateService` singleton tracks active runs cross-request; duplicate run returns 409
    - Returns HTTP 202 immediately; progress streamed via SignalR
12. Implement each agent as a Semantic Kernel function/plugin:
    - `StoryBibleAgent` — Phase 1: generates Story Bible JSON, streams with `AgentRole.StoryBibleAgent`
    - `CharactersAgent` — Phase 2: generates Character Cards JSON, streams with `AgentRole.CharactersAgent`
    - `PlotThreadsAgent` — Phase 3: generates Plot Threads JSON, streams with `AgentRole.PlotThreadsAgent`
    - `PlannerAgent` — Phase 4: generates Chapter Outlines JSON; also owns public Q&A helpers (`GatherInitialQuestionsAsync`, `AskQuestionsAsync`, `LoadExistingQaContextAsync`) called by `AgentOrchestrator`
    - `WriterAgent` — system prompt for creative writing, streams tokens via SignalR, uses RAG for prior chapter context
    - `EditorAgent` — system prompt for editing/improving prose
    - `ContinuityCheckerAgent` — system prompt for cross-chapter analysis, heavy RAG user
13. Implement question-pause mechanism:
    - Agent detects need for clarification (via tool call or special token in prompt)
    - Creates `AgentMessage` (Question), sets run to `WaitingForInput`
    - On user answer, run resumes with answer injected into chat history

### Phase 4: React UI — *parallel with Phase 3*
14. Scaffold React app with Vite + TypeScript:
    - Configure proxy to ASP.NET dev server
    - Install: `react-router`, `@microsoft/signalr`, `zustand` (state), `react-markdown`
15. Build pages/components:
    - **Dashboard**: List of book projects, create new book
    - **Book Detail**: Overview, chapter list with statuses, agent run buttons (disabled while running), spinner banner
    - **Chapter View**: Rendered markdown content, edit capability
    - **Agent Chat Panel**: Sidebar/panel showing agent messages, questions, answer input
    - **Settings**: LLM provider + Ollama model management (dropdown of installed/common models, pull with SSE progress), per-book language, per-agent system prompt overrides (collapsible)
    - **Login**: Login form (JWT sign-in; shows a one-time "sign in again" notice after the v0.3.0 switch)
    - **Admin → Users**: Admin-only page for user CRUD
    - **Real-time indicators**: Streaming text as agents write, status badges per agent, planning output progressively parsed into chapter cards (`parsePlanningStream`)
16. SignalR integration:
    - `useBookHub` hook connecting to `BookHub`
    - `useAuth` hook / `AuthProvider` context for current user state
    - Auth guard in `App.tsx` redirects unauthenticated users to `/login`
    - Live token streaming rendered in chapter view
    - Toast/notification when agent asks a question
17. Build React for production → output to `src/ABook.Api/wwwroot/`

### Phase 5: Docker & Integration — *depends on Phases 3 & 4*
18. Finalize multi-stage Dockerfile:
    - Stage 1: Build React (`node:20-alpine`, `npm run build`)
    - Stage 2: Build .NET (`mcr.microsoft.com/dotnet/sdk:10.0`, `dotnet publish`)
    - Stage 3: Runtime (`mcr.microsoft.com/dotnet/aspnet:10.0`, copy published + wwwroot)
19. Finalize `docker-compose.yml`:
    - `abook-api` service with environment variables (DB connection, Ollama URL)
    - `postgres` service with volume for data persistence
    - only two services in compose (no Qdrant service)
    - `extra_hosts: ["host.docker.internal:host-gateway"]` for Ollama access
20. ASP.NET SPA fallback middleware to serve React static files for all non-API routes

## Decisions

- **.NET 10** (latest; Docker images `mcr.microsoft.com/dotnet/sdk:10.0` + `aspnet:10.0`)
- **`.slnx` solution format** — requires .NET 9+ SDK (XML-based, lighter than classic `.sln`)
- **Ollama accessed via host.docker.internal** — not containerized, user manages it externally
- **LLM provider is pluggable** — abstracted behind `ILlmProviderFactory`, configured per-book or globally; supported: Ollama, OpenAI, GoogleAIStudio.
- **SK Ollama connector** is alpha (`Microsoft.SemanticKernel.Connectors.Ollama` 1.x-alpha); suppress `SKEXP0070` pragma
- **Agents use Semantic Kernel function calling** for the "ask question" tool — agent invokes a `AskUser` function which triggers the pause mechanism
- **Agent runs are fire-and-forget** — `AgentController` returns 202 immediately; `AgentRunStateService` singleton tracks state; duplicate run returns 409
- **Global agent run concurrency cap (env-based)** — `AgentRunStateService` enforces a process-wide max for simultaneous runs (`Running` + `WaitingForInput`) across all books/users. Configure via `AgentSettings__MaxConcurrentRuns` (`AgentSettings:MaxConcurrentRuns`), default `3`. Value is read at startup in `Program.cs`; changing it requires restart.
- **JWT authentication** — multi-user support with `IPasswordHasher<AppUser>`; admin role for user management
- **Per-book customization** — `Language` field and per-agent system prompt overrides stored on `Book` entity
- **Ollama model management** — `ModelsController` proxies Ollama's `/api/tags` and streams pull progress via SSE (replaced the old separate `OllamaController` file)
- **Markdown only** for book output — no DOCX/PDF export (can be added later)
- **pgvector for vector storage** — embeddings stored directly in PostgreSQL via the `vector` column type; no separate Docker service needed; `Pgvector.EntityFrameworkCore 0.*` package; dimension-free `vector` type to support any embedding model
- **Book continuation lineage**: `Books.BaseBookId` stores direct parent; parent-of-parent traversal is resolved at query time (cycle-guarded) so chains like A → B → C are supported without a closure table
- **Create-from-base behavior** (`POST /api/books` with `baseBookId`): copies language, human-assisted flag, target chapter count, all 7 system prompts, and book-scoped LLM config from base book to the new book; source ownership enforced
- **Ancestry-aware RAG retrieval**: `IVectorStoreService.SearchAsync` accepts `scopeBookIds`; `PgvectorVectorStoreService` filters `ChapterEmbeddings` via `BookId = ANY(array)` so descendant books can retrieve chunks from all ancestors
- **Ancestor planning context**: StoryBible/Characters/PlotThreads/ChapterOutlines generation injects a compact reference block built from ancestor books' Story Bible + active Characters (with Personality + Arc fields) + active Plot Threads + chapter synopses (all chapters for direct parent, last 5 for older ancestors). `IBookRepository.GetAncestorPlanningContextAsync` returns the data (`AncestorBookContext` per ancestor); `PromptTemplates.AncestorReference` formats it
- **Continuation-aware QuestionAgent**: `GatherQuestionsAsync` system prompt instructs the LLM to skip world-building questions already established by the ancestor context; focuses on continuation-specific decisions only
- **Checker → mechanical patch apply**: checker prompts categorize issues as `continuity`, `grammar`, `repetition`, or `style` with verbatim `originalText` (context-rich, min ~20 chars), `replacementText`, and an optional 1-indexed `position` line-number hint. `EditorAgent.EditAsync` dispatches to `ApplyPatchesAsync` when checker issues exist: patches located via IndexOf-first matching with whitespace normalization (`CRLF→LF`, trailing-trim), applied end-first to preserve offsets, position used as a disambiguator only for duplicate matches. `EditWithLlmAsync` handles manual edits / MCP tools without checker input. Feedback message grouped by issue type shows original → replacement + description per fix; unapplied patches reported factually with skip reason.

  - **Access token** — HS256 JWT (`JwtTokenService.CreateAccessToken`), 15 min by default (`Jwt__AccessTokenMinutes`), claims written with the full `ClaimTypes.NameIdentifier/Name/Role` URIs and `MapInboundClaims = false`, so controllers read the same claims as before. The SPA keeps it in memory only (`api.ts` session store) and sends `Authorization: Bearer`. SignalR passes it as `?access_token=` (`OnMessageReceived`, `/hubs` only) via `accessTokenFactory`.
  - **Refresh token** — 32 random bytes in the httpOnly, `SameSite=Strict` cookie `abook_refresh`, `Path=/api/auth`, 30 days by default (`Jwt__RefreshTokenDays`). The `RefreshTokens` table stores only its SHA-256 hash. `POST /api/auth/refresh` rotates it (old row revoked, `ReplacedByHash` set). Presenting a revoked token signs the user out everywhere (theft detection), except within 30 s of its rotation (parallel tabs), when an access token is returned without rotating again. Logout revokes the row; an admin password change revokes all of the user's rows. Expired/revoked rows older than 7 days are deleted at startup.
  - **Endpoints** — login/register/refresh return `{ user, accessToken, accessTokenExpiresAt, serverWarnings }`; logout is anonymous (the access token may have expired). `serverWarnings` is non-empty only for admins.
  - **Signing key** — `JwtKeyService` (singleton, initialised after migrations) uses `Jwt__SigningKey` (≥ 32 chars) when set; otherwise it generates a random key once, stores it in `ServerSecrets` (`Name = "Jwt:SigningKey"`), logs a ⚠️ warning at every startup and sends an admin `serverWarnings` banner. `dotnet ABook.Api.dll secrets show` (`SecretsCommand`, runs before the web host is built) prints stored secrets as env lines. The JwtBearer handler resolves the key per request (`IssuerSigningKeyResolver`) because it is only known after the database is migrated.
  - **Browser requests that cannot carry a header** — export downloads use `downloadFile` (axios blob + object URL); images use `useAuthedImage` (blob URL; the image responses are immutable so the HTTP cache still applies); the Ollama pull stream uses `authFetch`.

- **ApiToken auth for MCP**: `ApiTokenAuthenticationHandler` implements `Authorization: Bearer {guid}` scheme registered as `"ApiToken"` alongside the JwtBearer scheme (it ignores bearer values that look like a JWT). MCP endpoint accepts either scheme. `AppUser.ApiToken` column (nullable string) added via `AddApiToken` migration. Plaintext GUID — acceptable for local dev tool; threat model excludes DB-level attackers.
- **One token per user**: simple UX; regenerate to rotate via `POST /api/auth/api-token/regenerate`. `GET /api/auth/api-token` returns current token for display.

Controls whether the `/library` page and `/api/public/*` endpoints allow fully anonymous access (public mode) or restrict to "your own books only, must be logged in" (non-public mode, the default).

All wrap item parsing in `try/catch` to skip malformed partial JSON.

## Resilient JSON planning agents (Characters / Plot Threads / Chapter Outlines)

- **`PartialJson` (`src/ABook.Agents/PartialJson.cs`)**: recovers usable JSON from a response that was cut short mid-stream. `SalvageArray(raw)` strips reasoning tags (an *unterminated* `<think>` means the stream died while reasoning, so everything from it is dropped) and markdown fences, then walks the array tracking bracket depth and string/escape state, returning the top-level elements that finished plus a synthetic `]`. Candidate `[` positions are probed in order and only arrays **of objects** are accepted, so bracketed prose ("the [requested] list") never masks the payload. `IsComplete(raw)` reports whether the array was actually closed — used to detect a clean stream end on a truncated array (model hit `MaxTokens`).
- **`AgentBase.StreamJsonResponseAsync`**: wraps `StreamResponseAsync` and returns `(Raw, Failure)` instead of throwing. On any error — provider timeout, dropped connection, user Stop — it pulls the accumulated text from `AgentRunStateService.GetStreamBufferContent` so tokens the author already watched stream in are never discarded. `AgentBase.Rethrow` preserves the original stack trace; `AgentBase.SerializeForPrompt` renders saved planning data as camelCase JSON with the relaxed encoder (non-Latin scripts stay readable).
- **Keep-partial-on-failure**: `CharactersAgent`, `PlotThreadsAgent` and `PlannerAgent` each salvage what streamed, **merge** it into the existing set (never replace), write versions + an `"agent-partial"` snapshot, post a `SystemNote` naming how many items were kept, and then rethrow so the run is still marked Failed and the phase stays incomplete. The next run continues from there. Merge keys: `Name` (case-insensitive) for characters and plot threads, `Number` for chapters — `MergeCharacterCardsAsync`, `MergePlotThreadsAsync`, `MergeChapterOutlinesAsync` on `IBookRepository`.
- **Empty or truncated results never wipe data**: all three parsers throw `FormatException` when zero usable items are parsed, and a response that ends without closing the array is treated as a failure (salvage + merge + rethrow) rather than a complete set.
- **`LenientJson` (`src/ABook.Agents/LenientJson.cs`)**: reads planning fields without trusting the model to honour the schema's types. OpenAI-compatible endpoints (LM Studio, Ollama, vLLM) routinely return an integer as `1.0` or `"3"` and a text field as an array or a bare number, all of which make the strict `JsonElement` accessors throw. `Int` accepts integers, non-integral numbers (rounded), numeric strings, and numbers embedded in prose (`"Chapter 4"` → `4`), yielding `null` when nothing is recoverable; `Text` coerces any value kind, flattening arrays to a comma-separated list. Used by all four planning parsers.
- **`PlanningParse` (`src/ABook.Agents/PlanningParse.cs`)**: makes a planning failure self-describing. `OpenArray`/`OpenObject` replace the bare `JsonDocument.Parse` and turn "no JSON", "invalid JSON" and "root was not an object" into messages that name the agent and quote what the model actually returned (whitespace-collapsed, 300-char snippet). `SkipNote` describes one rejected element by index, reason, and its raw JSON; `SkipSummary` explains an all-rejected outcome; `KeptSummary` reports the drops on an otherwise successful run.
- **Per-element resilience**: each array parser wraps one element at a time. A malformed entry — no `name`, or any exception while reading it — is dropped with a reason into a `List<string> skipped` collector rather than aborting the run, so one bad entry no longer costs the author the whole set. On success with a non-empty collector the agent logs a warning and posts a `⚠️` `SystemNote` via `AgentBase.ReportNoteAsync` (a non-fatal counterpart to `ReportErrorAsync` — it writes the note and refreshes messages, but raises no `AgentError` signal). All keep-partial and Story Bible failure notes now append `Reason: {ex.Message}` so the underlying cause reaches the chat instead of being replaced by generic advice.
- **Existing content is fed back to the LLM**: each of the three agents loads its already-saved, non-archived rows and appends a block to the user prompt ("These … are already saved for this book: `[…]` — return the complete, updated set, keeping each item's exact `name`/`number` so it can be matched; items you leave out will be removed"). Chapters additionally carry an `alreadyWritten` flag so the model does not re-premise a chapter whose prose exists.
- **Archived content is invisible to agents**: agents read via `GetCharacterCardsAsync` / `GetPlotThreadsAsync` / `GetChaptersAsync` (all `!IsArchived`), and `DeleteCharacterCardsAsync` / `DeletePlotThreadsAsync` / `ReplaceChaptersAsync` now delete **only non-archived rows** — an agent re-run can no longer destroy archived items (this also protects them during snapshot restores, which reuse the same delete helpers).

## Archived content is display-only (v0.1.22)

The invariant: **an archived chapter, character card, or plot thread exists only to be rendered in the UI's archived sections.** It never reaches a model prompt, never lands in an export, and is never mutated by an agent. Enforced at four layers:

- **Repository reads** — `GetChaptersAsync` / `GetCharacterCardsAsync` / `GetPlotThreadsAsync` filter `!IsArchived` at the DB level, and `GetAncestorPlanningContextAsync` applies the same filter when pulling a sequel's ancestor context. `GetChapterAsync` deliberately does **not** filter: the UI must be able to load an archived chapter to display and restore it.
- **Book loading** — `GetByIdWithActiveDetailsAsync` mirrors `GetByIdWithDetailsAsync` but with a filtered `Include` on `Chapters`. `AgentOrchestrator.RunPlanningPipelineAsync`, `ContinuityCheckerAgent.CheckAsync`, `BookExportService.ExportAsync`, and `PublicController.GetBook` all use the active variant. `GetByIdWithDetailsAsync` returns everything and is reserved for `BooksController.GetById`, which feeds the UI's archived sections.
- **Agent entry guards** — `AgentBase.EnsureNotArchived(chapter)` throws when an agent resolves an archived chapter by id. Applied in `WriterAgent.WriteAsync`, `EditorAgent.EditAsync`, and `ContinuityCheckerAgent.PreWriteCheckAndFixAsync`, i.e. every place an agent turns a `chapterId` into a `Chapter`.
- **API and MCP surfaces** — `AgentController.Write`/`Edit` and the `write_chapter`/`edit_chapter` MCP tools reject an archived target before scheduling the fire-and-forget run, so the caller gets a 400 / `McpException` rather than a run that fails later. The `update_chapter`, `update_character`, and `update_plot_thread` MCP tools refuse to modify archived rows; `get_chapter` refuses to serve archived prose.

**RAG** is already covered independently: `PgvectorVectorStoreService.SearchAsync` joins back to `Chapters` and requires `IsArchived = FALSE`, for both versioned and legacy chunks. Chunks are left in place when a chapter is archived so restoring it brings its embeddings back.

**Exports** filter `!IsArchived` a second time inside `GenerateHtml`, `GenerateFb2`, `GenerateEpub`, and `MetadataExport.Generate` — defence in depth, and the seam the unit tests pin the invariant at.

## Stability & safety guards (v0.2.0)

- **One place for LLM text** — every prompt string lives in `AgentPrompts.cs` (`DefaultPrompts`, `PromptTemplates`, `RagQueries`). Agents gather data and call the templates; they never build prompt text. The repository no longer formats prompts either: `GetAncestorPlanningContextAsync` returns data, `PromptTemplates.AncestorReference` formats it.
- **Starting a run** — `AgentRunnerService.TryStart(bookId, role, chapterId, action)` is the only entry point (REST and MCP). It calls `AgentRunStateService.TryStartRun`, which under one lock checks book-busy + global capacity, sets `Running`, and creates the run's `CancellationTokenSource`; only on success is the orchestrator call started. This closed a race where two quick starts both passed the old unlocked `EnsureCanStart`, the second disposed the first run's token and then marked the *running* run Failed. `ExecuteAgentRunAsync` now only asserts the slot is claimed. The runner's `finally` calls `ReleaseRunCts` to dispose the source.
- **Stop fail-safe** — `CancelRun` returns whether anything was cancelled; if a status is still active with no live cancellation source, it is forced to `Cancelled` so a book can never stay locked.
- **Run states** — `RunStates` constants (`Running`, `WaitingForInput`, `Done`, `Failed`, `Cancelled`) and `AgentRunStatus.IsActive` replace string literals.
- **Failure handling never masks success** — `ExecuteAgentRunAsync`'s success bookkeeping sits outside the `try`, and every UI notification in the terminal paths goes through `NotifySafelyAsync`, so a SignalR hiccup can neither turn finished work into "Failed" nor skip the error report.
- **Streaming** — `StreamResponseAsync` applies an idle timeout between chunks (`TimeoutMs`, default 5 min) through a linked token, so a connection that stalls mid-response fails instead of hanging the run and its concurrency slot. The accumulated buffer is a locked `StreamBuffer` (the refresh-restore endpoint reads it concurrently). `stopStreamingAt` matches only a line-aligned tail window instead of the whole buffer on every chunk. The Ollama and OpenAI-compatible clients share one connection pool (`LlmHttp`).
- **Thinking output** — never streamed. Provider reasoning chunks and inline `<think>`/`<thinking>` sections (split out live by `InlineThinkSplitter`) are collected separately and saved as one "💭 Thinking" SystemNote when the call ends — on success, failure, timeout or Stop — followed by `MessagesUpdated` so the chat refreshes. The content stream, refresh-restore buffer and JSON salvage therefore carry content only.
- **Only book content streams** — `forwardToUi: false` for question gathering and all Continuity Checker calls (their output is not shown in the content views; question text used to land in the chapter-outline preview).
- **Auth** — `AgentController` (plus ownership on every action), `ModelsController` and `BookHub` (ownership check in `JoinBook`) require sign-in. MCP `stop_workflow`, `answer_agent_question` and `get_agent_status` now check ownership; `get_agent_status` reports `running` from `IsActive`; `run_continuity_check` honours `chapterId`.
- **Run state survives refresh** — every agent announces its step through `AgentBase.ReportRunningAsync`, which updates the server-side status (`AgentRunStateService.UpdateRunRole`) as well as broadcasting `AgentStatusChanged`, so `GET agent/status` reports the current role and chapter instead of the role the run started with. `SignalRBookNotifier` records the latest `WorkflowProgress` message (`SetLastProgress`, cleared by `TryStartRun`). Each `StreamBuffer` is `Begin(live)`-ed per call and `End()`-ed when it finishes; `HideFrom` marks where forwarding stopped (`stopStreamingAt`, failure flush) so `VisibleText()` is exactly what the UI was sent. For an active run `GET agent/status` adds `step` and `stream` (`GetLiveStream`: the live call's role, chapter and visible text). `BookContext.syncRunState` applies it on load and after every hub (re)join: run status, the step (seeds `workflowLog`), the pending question, and the stream — routed by the same `writeStream` as live tokens. Tokens that arrive while the request is in flight are captured and merged onto the snapshot by overlap, so nothing is dropped or doubled. Because the join comes first, no token falls between the snapshot and the live feed.
- **Restart recovery** — see Durable run persistence: waiting runs are orphaned too, their question resolved, and the author told to use Continue.
- **UI resilience** — `useBookHub` rejoins the book group on reconnect (a reconnect gets a new connection id) and retries the initial connection; `BookContext` then re-reads messages, book, token stats and run status. `refreshMessages` ignores out-of-order responses and clears a pending question answered elsewhere; answers broadcast `MessagesUpdated`. An `ErrorBoundary` keeps a render error from blanking the app, a 401 anywhere signs the user out of the SPA, and a failed answer submission is shown instead of swallowed (Skip now really sends an empty answer).
- **Health** — anonymous `GET /health` checks database connectivity.
- **CI** — the test job also type-checks the UI (`tsc --noEmit`); the Docker build runs only `vite build`, which does not.

## Illustrations (Z-Image)

Images are generated in two separate runs because the text model and the image model rarely fit in VRAM together:

1. **Planning — LLM only** (`IllustrationPlannerAgent`, role `IllustrationPlanner`, run type `illustrate-plan`). When `Book.IllustrationsEnabled`, `ProcessChapterAsync` plans each chapter right after it is marked Done, and the workflow plans the cover after the final continuity check. A planning failure is posted as a note and never fails the chapter. Manual runs: `POST /api/books/{id}/illustrations/plan {scope: Missing|Chapter|Cover|Characters, targetId}`.
   - `EnsureStyleSheetAsync` runs first: when the book has no art direction, or the configured `ImageVisualStyle` differs from `IllustrationStyleSource`, the LLM writes it once (`PromptTemplates.StyleSheetUser`, schema `StyleSheet`): a style description, the portrait composition shared by the whole cast, and a book-wide negative prompt. Scope `Style` forces a rewrite; `PUT .../illustrations/style` edits it. `ApplyStyleSheetAsync` rebuilds every portrait prompt and marks rendered images for re-rendering when it changes.
   - `EnsureCharacterVisualsAsync` writes a `VisualPrompt` (body only — no clothing) and a `usualOutfit`, stored as the character's usual-outfit `VisualAsset`; the portrait prompt is built by code as `PortraitPrompt(framing, visualPrompt, outfit)`, so every portrait has the same composition for every active character whose `VisualPromptSourceHash` no longer matches (or who has no portrait). Seeds come from FNV-1a of `"{bookId}|{lower-cased name}"`, so they survive a Characters re-run that recreates the cards.
   - `PlanChapterAsync` sends the chapter as `[N]`-numbered paragraphs plus every character's visual description, the registered visual assets and the full prompts of the last three scenes before the chapter; the prompt asks for `ImagesPerChapter` images (configurable, default 2) as a guide the model may exceed when the chapter genuinely needs more, and the model writes both prompts. Each scene lists the recurring `assets` it shows (before its prompt, so they are written first); new ones are registered as the scene is persisted (`RegisterAssetsAsync`), and a prompt that pasted a reworded description of a known asset is corrected to the canonical wording. Scenes are saved as they stream: `StreamResponseAsync`'s `onElementClosed` callback re-parses the partial response (`PartialJson.SalvageArray`) whenever a chunk closes a JSON element and persists each newly finished scene, so the author sees them appear one by one and an interrupted call keeps them (with a chat note). The first saved scene replaces the chapter's never-rendered plan via `ReplaceUnrenderedIllustrationsAsync`; a failure before any scene arrives leaves the old plan intact. Rendering was already incremental — every image is saved as soon as it returns.
   - All prompt text is in `AgentPrompts.cs`: `DefaultPrompts.Illustrator` (overridable per book, `{VISUAL_STYLE}` placeholder), `PromptTemplates.CharacterVisualsUser / ChapterIllustrationsUser / CoverUser`; schemas in `JsonSchemas`. Calls use `forwardToUi: false`. No negative prompt, content rule or image count is imposed by code — the model decides per genre. Negatives are never relied on: Z-Image Turbo ignores them at CFG 1.0, so the prompt tells the model to make every image come out right from its positive prompt alone (say what is there, never name what should be absent), and `{NEGATIVE_PROMPTS}` (`PromptTemplates.NegativePromptSupport`) states whether negatives take effect at the configured CFG — at most an optional extra safeguard.
2. **Rendering — image model only** (`IllustrationRenderer`, role `Illustrator`, run type `illustrate`). `POST .../illustrations/render {scope: All|Portraits|Chapter|Character|Single, targetId, reroll}`. Order: optional Ollama unload (`ILlmModelUnloader`, `keep_alive: 0`), a `/health` check, portraits, cover, scenes in reading order. Each image is saved (`SaveRenderedImageAsync`) and announced with the `IllustrationsUpdated(bookId, illustrationId)` SignalR event; a failed image is marked Failed with its reason and the run continues.

**Style consistency** — the renderer prepends the book's art direction word for word to every prompt (`ComposePrompt`) and merges the book-wide negative into each image's (`ComposeNegative`); the planner is told to describe content only and never restate the style. A single "cast sheet" image was rejected: Z-Image takes no reference image, so it could not carry over to the separate portrait and scene renders, and many people in one image blend identities.

**Object, outfit and place consistency** — `VisualAsset` registry. Z-Image takes no reference images, so identical wording is the only thing that keeps a prop, an outfit or a place identical between images. Every scene/cover plan lists the recurring assets it shows; the planner copies a registered asset's description word for word, or registers a new one with its canonical description (`PromptTemplates.VisualContinuityRule`, repeated in every scene and cover request). Characters wear their usual-outfit asset unless the story dresses them differently, in which case the planner registers an outfit asset ("Mara — wedding gown") and keeps it on for that stretch of the story. Editing an asset (`PUT .../illustrations/assets/{id}`, MCP `update_visual_asset`) replaces the old wording in every prompt and marks those illustrations for re-rendering; `GET/POST/DELETE .../illustrations/assets` list, add and remove them.

**Character consistency** (what worked in adate — Z-Image takes no reference images): one seed per character used for the portrait and every scene whose `FocusCharacterId` is that character, plus the character's `VisualPrompt` repeated word for word in each prompt. Re-rolling a portrait makes its new seed the character's; re-rolling a scene pins `Illustration.Seed`. Editing a character's visual description (`PUT .../illustrations/characters/{id}/visual`) or regenerating it replaces the old wording in every prompt that quotes it and marks those illustrations for re-rendering.

**Placement** — `ParagraphAnchors` (Core) splits content into paragraphs (runs of non-blank lines; `utils/paragraphs.ts` mirrors it) and resolves `AnchorText` with quote/whitespace/emphasis-insensitive matching, falling back to the clamped `ParagraphNumber`. The API returns the resolved `paragraphIndex`, so prose edits don't strand images.

**Editing** — changing prompt, negative prompt, orientation or focus character sets a Rendered illustration back to Planned; it keeps showing (and exporting) its previous image until re-rendered.

**Image client** — `ZImageImageGenerator` (Infrastructure/Imaging) talks to the self-hosted Z-Image API from adate's `compose/zimage`: `POST /generate` (snake_case JSON, sized body) → `{image_id, seed}`, then `GET /images/{id}` (PNG signature checked); FastAPI's `detail` is put into the error. `UnslothStudioImageGenerator` talks to Unsloth Studio's native image API with `Authorization: Bearer sk-unsloth-…`: `GET /api/inference/images/status`, then `POST /api/inference/images/generate` (`prompt`, `negative_prompt`, `width`, `height`, `steps`, `guidance`, `seed` ≤ 2^53−1; unset steps/CFG are omitted so Studio's 9 / 0.0 apply) → `{images:[{url, seed}]}`, then the gallery `url`. Studio's OpenAI-shaped `/v1/images/generations` is deliberately not used — it ignores seed, steps, guidance and negatives, and the seed is what keeps characters consistent. The endpoint may be given with or without `/v1`. Studio keeps one heavy model on the GPU (its `gpu_arbiter`), so serving the text model from the same Studio evicts the image model: before every image the client checks status and, when nothing is loaded and `ImageModel` is set (`owner/repo` or `owner/repo:file.gguf|.safetensors`), `POST /images/load`s it and polls status / `load-progress` (up to 30 min, cancellable). Its health check reports `idle` (ready) in that case, and the renderer posts a progress note. Shared HTTP plumbing (client, bearer header, sized JSON body, PNG check, FastAPI/OpenAI error-envelope parsing) is in `ImageHttp`. `IImageGeneratorFactory` picks the client by `ImageProvider`. "Test connection" is `POST /api/configuration/image-health` (body, so the key stays out of URLs).

**Export** — `BookExportService.LoadArtAsync` collects every illustration with an image and re-encodes it with `ExportImageCompressor` (SkiaSharp): JPEG quality 82, longest side capped at 1600 px, flattened onto white; the original is kept when it can't be decoded or the JPEG would not be smaller. Stored images stay lossless PNG. HTML embeds data URIs; EPUB adds `OEBPS/images/*`, manifest items, a `cover-image` item and `cover.xhtml`; FB2 adds `<coverpage>`, `<image l:href>` in sections and `<binary>` blocks; the metadata export embeds only the character portraits (compressed the same way) and lists every illustration's plan and render without its image. Converters run per paragraph (`WithFigures`) so figures follow their paragraph.

**UI** — Illustrations page (`/books/:id/illustrations`: cover, portraits, per-chapter scenes, Plan/Render buttons), figures inline in `ChapterView` and the public reader (`ChapterContent` + `IllustrationFigure`), portrait + visual description on the Characters page, `ImageGenSettingsFields` in the global/book LLM settings and the preset form. Recurring assets are listed and editable in their own section of the Illustrations page (`VisualAssetsCard`). MCP: `list_illustrations`, `update_illustration`, `list_visual_assets`, `update_visual_asset`, `plan_illustrations`, `render_illustrations`; image fields in `set_llm_config` / presets; `illustrationsEnabled` in `update_book`.
